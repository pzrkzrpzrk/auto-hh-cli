## Проблема

### D5 — мапа «vacancy → запись дайджеста» объявлена дважды в одном файле

- `src/cli/cmd-digest.ts:132-141` — для `rejected` (внутри `selectAccepted` :114-151)
- `src/cli/cmd-digest.ts:159-170` — для `matched` (внутри `buildResults` :155-183)

Одни и те же 11 полей. При этом тип `DigestEntry` уже есть в `src/types.ts:44-55` (и используется как
тип Mongo-документа в `src/store/digest-store.ts:4`), но **эти литералы им не типизированы** — то есть
добавление нового поля не будет поймано компилятором ни в одной из двух копий.

### K5 — `onBatch` отдаёт накопленную карту

`src/domain/cover-letter/cover-letter.ts:174-176`: колбэк получает **всю накопленную** карту писем, поэтому
`coverDigest` при каждой новой пачке перезаписывает в MongoDB письма **всех** предыдущих пачек.
При 1000 вакансий и пачках по N это квадратичная запись.

## Риски

Это единственный тикет, где правка контракта может привести к **потере данных** (письма перестанут
дописываться). Поэтому:
- сначала сделать T-06 (механика пула) и T-07 (единый merge писем) — они уберут дублирование вокруг;
- проверять строго по count в `cacheCoverLetters` до и после прогона;
- если прогон невозможен (нет ключа ИИ), оставить правку последней и перенести проверку на реальный запуск,
  пометив тикет как «требует проверки на живых данных».

## Реализовано

1. `cmd-digest.ts`: добавлена `toDigestEntry(full, { score, reason, comment, coverLetter }): DigestEntry` —
   единственный литерал записи дайджеста; `id` приводится к строке (`String(full.id)`), потому что тип
   `DigestEntry.id` — `string`, а письма ищутся по `String(id)`.
   Обе копии заменены: `rejected.push(toDigestEntry(full, { …, comment: null, coverLetter: '' }))` и
   `matched.push(toDigestEntry(full, { …, coverLetter: '' }))`.
   **Решение по `comment` для `rejected`:** передаётся `null`, как и раньше — иначе `rejected-*.md`
   (`digest-store.ts:25` печатает `comment` при истинности) начал бы выводить ещё и «Совпадение: …»,
   то есть изменился бы формат файла. Набор полей при этом единый — различаются только значения.
2. `cover-letter.ts`: `runBatch` собирает письма текущей пачки во временную `fresh` и вызывает
   `onBatch(fresh)` только если `fresh.size` (инкрементально); накопительный `result` возвращается как раньше.
   JSDoc `buildCoverLettersBatch` обновлён.
3. `cmd-cover.ts` менять не пришлось: колбэк уже итерируется по переданной карте, поэтому под новым
   контрактом он пишет в Mongo ровно письма текущей пачки (до правки — всю накопленную карту).

### Проверки

- `npx tsc --noEmit` → exit 0; `toDigestEntry` — 1 определение + 2 вызова; литералов из 11 полей вне неё нет.
- **Контрактный тест на мок-сервере** (без реального ИИ и без записи в Mongo): `baseUrl` в `CONFIG_PATH`
  указан на локальный HTTP-мок, 5 вакансий, `batchSize = 2`.
  Результат: 3 запроса на `/v1/chat/completions`; размеры `onBatch` — **`[2,2,1]`** (накопительно было бы
  `[2,4,5]`); итоговый `result.size = 5`, ключи `["1","2","3","4","5"]`. Временный чек-файл удалён.
- Живая проверка потребителя без генерации: `npx tsx bin/auto-hh cover --limit 2` → «письма уже есть: 2,
  генерируем: 0», письма напечатаны, `cacheCoverLetters` **154 → 154** (перезаписи нет).
- Не проверено (нужен реальный ключ/живой прогон): фактическая запись писем всех пачек при `cover` с ИИ.
  Логика записи при этом одна и та же (`saveLetter` на элемент пачки), объём данных не уменьшается,
  поэтому риск потери данных считается закрытым статически + мок-тестом.
